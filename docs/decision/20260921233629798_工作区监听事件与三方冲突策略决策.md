# 决策记录：工作区监听事件与三方冲突处理策略

> 决策时间：2026-09-21 23:36:29
> 状态：已采纳并落地
> 关联工作流：W3 Workspace watcher 与三方冲突

## 1. 背景

v0.3.2 的前端每 1.5 秒轮询当前标签的 `modified` 时间戳，存在三个问题：

1. 只能感知活动标签，非活动标签的外部修改会被遗漏。
2. 重命名与删除无法可靠识别，只能通过时间戳变化猜测。
3. dirty 文件被外部修改时，前端只写入 `externalModifiedAt`，没有统一的冲突状态，用户在保存时仍可能覆盖磁盘内容。

后端原有 `services/file_watcher.rs` 存在实现但未接入 Tauri 生命周期，也没有事件出口。

## 2. 决策

### 2.1 监听层放在 Rust 后端，前端只消费事件

采用 `notify` 6 的 `RecommendedWatcher` 递归监听工作区根目录，事件通过 `workspace:file-changed` 推送给前端。

理由：Tauri 前端无法访问原生文件系统事件；后端监听可以在单线程事件循环中完成去抖合并，避免每个标签各自轮询。

代价：需要新增 Tauri managed state 与三个命令，进程退出时需显式释放。

### 2.2 单工作区监听 + 显式启停

`WorkspaceWatcherState` 同一时间只持有一个工作区监听；`start` 会先停止旧监听，`stop` 释放 watcher 与后台线程。

理由：当前产品形态是单工作区编辑器，多根目录监听会显著增加事件去重与生命周期复杂度，收益不足。

### 2.3 去抖 250 ms，范围限制 50-2000 ms

后端统一 clamp 调用方传入的去抖值，默认 250 ms。

理由：250 ms 能覆盖绝大多数编辑器保存动作的落盘抖动，又不会让用户感知到延迟；上下限避免调用方传入 0 造成事件风暴或传入过大值导致长时间无反馈。

### 2.4 原子替换归一为 `modified`

写入类操作常见模式是「写临时文件 → 原子 rename 到目标」。这类 rename 不应被当作用户重命名，事件归一为 `modified`；只有单路径 rename 且旧路径不在忽略列表时才输出 `renamed`。

理由：把原子保存识别成重命名会导致前端误改标签路径，甚至丢失打开状态。

### 2.5 忽略目录与临时文件在事件源过滤

忽略 `.git`、`node_modules`、`target`、`dist`、`.next`、`.idea`，以及 `.DS_Store`、`Thumbs.db`、`desktop.ini`、`*.tmp`、`*.swp`、`*~` 等临时文件；同时忽略 Access 类事件。

理由：这些路径与事件不会影响用户内容，却会淹没真实变更，尤其是构建目录与编辑器 swap 文件。

### 2.6 dirty 文件一律不自动覆盖

前端策略分三类：

1. dirty 标签：写入 `fileConflicts` 记录 + `externalModifiedAt`，只提示不覆盖，由用户选择重载 / 保留 / 另存为。
2. clean 标签：直接重载并清除冲突记录。
3. 已删除文件：记录 `removed` 冲突，不自动关闭标签，避免丢失内存内容。

理由：编辑器第一原则是不静默破坏用户输入。自动覆盖或自动关闭都可能造成不可恢复的数据丢失。

### 2.7 监听失败必须退化，不允许静默失效

`start` 返回 `false` 或事件订阅抛错时，前端回退到原有 1.5 秒轮询，并让轮询路径同样写入冲突记录。

理由：原生监听在容器、网络盘、权限受限目录上可能失败；静默失效会让用户以为「不会丢数据」而实际失去保护。退化后行为一致，只是延迟变大。

## 3. 备选方案与结论

| 方案 | 说明 | 结论 |
|---|---|---|
| 继续纯前端轮询 | 改动最小，但只能覆盖活动标签 | 拒绝，无法覆盖非活动标签与重命名 |
| 每个标签单独监听文件 | 事件精确到文件 | 拒绝，句柄数量随标签增长，跨平台差异大 |
| 多工作区监听 | 同时监听多个根目录 | 暂缓，当前产品为单工作区形态 |
| 监听事件直接覆盖 dirty 内容 | 实现简单 | 拒绝，违反不静默丢数据原则 |
| 后端监听 + 前端冲突状态（采纳） | 后端去抖、前端决定策略 | 采纳 |

## 4. 影响

- 新增 Tauri managed state：`WorkspaceWatcherState`，注册于 `lib.rs`。
- 新增事件契约：`workspace:file-changed`，载荷为 `WorkspaceFileChange[]`（camelCase 字段）。
- 新增命令：`start_workspace_watch`、`stop_workspace_watch`、`workspace_watch_status`。
- 前端新增 `fileConflicts` store 作为冲突唯一来源；轮询路径也写入同一 store。
- 删除未接入的 `services/file_watcher.rs`，避免双实现并存。

## 5. 回滚

1. 前端 `startExternalFileWatch` 已内置退化路径，禁用 watcher 命令即可回到 1.5 秒轮询。
2. Rust 侧删除 `WorkspaceWatcherState` 注册与 3 个命令即可恢复原状，不影响文件读写与 workspace runtime。
3. 冲突记录仅存在于前端内存 store，清空标签或重启应用即自然失效，无持久化迁移成本。
