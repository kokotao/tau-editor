# ADR：恢复库 v2 使用 app-data 分文件存储

> 决策时间：2026-09-21 23:19
> 状态：已采纳（v0.3.3 W2 落地）
> 相关文件：`frontend/src-tauri/src/services/recovery_store.rs`、`frontend/src/services/sessionService.ts`

## 背景

会话快照与未保存草稿此前保存在 WebView 的 `localStorage`（`text-editor-session-v1`、`text-editor-recovery-drafts-v1`）。该方案有三个问题：

1. 容量受限（多数平台 5 MB），大文件草稿写入直接失败且无法提示；
2. 与服务端/系统备份、清理策略无关，用户清理 WebView 数据会静默丢失草稿；
3. 没有生命周期管理，过期草稿永久残留。

## 决策

桌面端改用 Tauri `app_data_dir/recovery-v2` 作为恢复库，采用“会话单文件 + 草稿分文件”的目录结构：

```
recovery-v2/
  session.json
  drafts/<sha256(path 或 id)>.json
```

关键约束：

1. 所有写入走同目录临时文件 + `sync_all` + 原子替换 + 父目录同步；
2. 草稿键优先取文件绝对路径，未命名标签取标签 id，均可哈希后作为稳定文件名；
3. 限额为 40 条草稿 / 32 MiB 总量 / 30 天保留，读取时裁剪并删除落选文件；
4. 损坏、版本不符、超限的记录只记日志并跳过，不允许阻塞启动；
5. v1 数据在首次启动时迁移到 v2，写入成功后才删除旧键；迁移失败保留旧键下次重试；
6. Web 构建保留 `localStorage` 同构后端（`text-editor-recovery-v2`），限额与结构一致。

## 备选方案

- 继续扩展 `localStorage` 并手动分片：容量天花板仍在，且无原子性保证。
- 单文件集中存储全部草稿：每次写入都要重写整库，30～40 MB 量级下延迟与损坏半径都不可接受。
- 引入 SQLite 存草稿正文：需要迁移既有存储与查询层，收益不足以覆盖本轮成本，留待后续按需演进。

## 影响

- 前端 `sessionService` 全面异步化，`App.vue` 启动与关闭路径需要等待初始化与落盘；
- Tauri 关闭请求改为“先落盘再销毁窗口”，`WindowService` 暴露 `onBeforeClose` 钩子；
- 备份与清理恢复数据只需处理 `recovery-v2` 目录；
- 若恢复库整体损坏，最坏结果是回到“无会话可恢复”，不会影响用户磁盘上的正式文件。

## 回滚

删除 `app-data/recovery-v2` 目录并把 `sessionService.ts` 还原到 v1 实现即可回退；回退前若已执行过迁移且旧键已被删除，v1 时代的历史草稿不可再次迁移。
