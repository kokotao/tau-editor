# macOS「已损坏」问题：签名与公证交付策略

- 文档类型：决策记录（Decision）
- 日期：2026-09-26
- 目标版本：`v0.4.2`
- 状态：已实施（构建期 ad-hoc 签名 + CI Developer ID/公证开关）
- 影响范围：`frontend/src-tauri/tauri.conf.json`、`.github/workflows/release.yml`、`scripts/package-macos-app.sh`、README/INSTALL macOS 安装说明

## 1. 问题

macOS 用户从浏览器下载 DMG、把 App 拖到「应用程序」后，首次打开提示：

> “Tau Editor”已损坏，无法打开。你应该将它移到废纸篓。

当前规避方式是让用户手工执行一次：

```bash
xattr -cr "/Applications/Tau Editor.app"
codesign --force --sign - "/Applications/Tau Editor.app"
```

需要回答两件事：

1. 这套修复动作能否在安装完成后自动执行？
2. 是否存在不需要用户手工操作的替代方案？

## 2. 结论

- `.app` 拖拽安装没有 post-install 钩子；Gatekeeper 在应用进程启动之前就完成校验，应用自身代码没有机会执行修复。因此**当前分发形态下无法做到安装后自动执行**。
- 已定位到真正的构建缺陷：旧产物只带链接器的 ad-hoc 签名，`Info.plist` 未绑定、资源未封装，`codesign --verify` 直接失败。这正是 macOS 报「已损坏」的技术原因。
- 解决方案分两层：
  - **立即生效（零成本）**：在 Tauri 构建期设置 `bundle.macOS.signingIdentity = "-"`，对整个 `.app` 做 ad-hoc 签名。产物签名完整可校验，不再触发「已损坏」；用户只需在「系统设置 → 隐私与安全性」点击一次「仍要打开」。
  - **彻底免提示**：使用 Apple Developer ID Application 证书签名并公证（notarization）+ staple。CI 已支持，配置 Secrets 即启用，不需要改代码。
- `.pkg` + postinstall 脚本可以做到「安装后自动执行 xattr/codesign」，但 `.pkg` 本身同样受 Gatekeeper 拦截，用户仍要放行一次；且需要额外维护安装器与脚本，收益低于 ad-hoc + 系统设置放行，因此不作为默认方案。

## 3. 根因证据

修复前对本地构建产物执行：

```bash
codesign -dv --verbose=4 "Tau Editor.app"
codesign --verify --deep --strict --verbose=2 "Tau Editor.app"
```

关键输出：

```text
CodeDirectory ... flags=0x20002(adhoc,linker-signed)
Info.plist=not bound
Sealed Resources=none
Internal requirements=none

Tau Editor.app: code has no resources but signature indicates they must be present
```

说明只存在 `Mach-O` 的 linker 签名，没有完整的 bundle 签名：

- `Info.plist` 未绑定；
- `Contents/Resources` 未封装；
- 无 `Contents/_CodeSignature/CodeResources`。

浏览器下载会写入 `com.apple.quarantine`，Gatekeeper 对「签名不完整」的判定结果就是「已损坏」，而不是可放行的「未验证开发者」。

执行一次完整 ad-hoc 签名后实测：

```text
flags=0x2(adhoc)
Info.plist entries=15
Signature=adhoc

valid on disk
satisfies its Designated Requirement
```

## 4. 方案对比

| 方案 | 用户操作 | 成本 | 结论 |
|---|---|---|---|
| 继续让用户执行 `xattr` + `codesign` | 终端命令，且每次重装/升级都要做 | 0 | 体验最差，不作为默认 |
| 构建期 ad-hoc 签名（`signingIdentity: "-"`） | 首次打开在「隐私与安全性」放行一次 | 0 | 已采用为默认回退 |
| Apple Developer ID 签名 + 公证 + staple | 无提示 | Apple Developer 账号（99 美元/年） | 已接入 CI，配置 Secrets 即生效 |
| `.pkg` + postinstall 执行 `xattr`/`codesign` | 放行 `.pkg` 一次，安装后自动 | 需维护安装器，且 pkg 未签名同样被拦 | 备选，不默认发布 |
| Homebrew Cask `--no-quarantine` | 终端执行 `brew install` | 需维护 Cask | 仅作为补充渠道 |

补充说明：应用内自动更新（Tauri updater）下载的文件不由浏览器写入隔离属性，因此首次安装解决后，后续应用内升级通常不会再次触发该问题。

## 5. 已实施改动

1. `frontend/src-tauri/tauri.conf.json`
   - `bundle.macOS.signingIdentity` 设为 `"-"`，Tauri 打包时对整个 `.app` 做 ad-hoc 签名（在 DMG 生成之前）。
   - 该配置只影响 macOS bundle；本地开发与 Windows/Linux 构建不受影响。
2. `.github/workflows/release.yml`
   - 新增 `Configure Apple code signing`：仅当 `APPLE_CERTIFICATE` Secret 存在时，把证书与公证凭据写入 `$GITHUB_ENV`；缺少必需的 `APPLE_SIGNING_IDENTITY` 或公证凭据时直接失败，避免产出不可发布的包。
   - 新增 `Verify macOS code signature`：始终执行 `codesign --verify --deep --strict`；Developer ID 模式下额外执行 `spctl --assess` 与 `xcrun stapler validate`。
   - `APPLE_SIGNING_IDENTITY` 环境变量优先级高于配置文件，因此配置了真实证书时会覆盖 `-`，走 Developer ID 签名。
3. `scripts/package-macos-app.sh`
   - 打包前清理隔离/溯源属性；发现签名无效且不是 Developer ID 签名（且未指定 `APPLE_SIGNING_IDENTITY`）时自动补 ad-hoc 签名并校验。
4. `README.md` / `INSTALL.md`
   - 更新 macOS 首次打开说明：默认只需在「隐私与安全性」放行一次；保留旧版本「已损坏」的手工修复命令；补充 Developer ID Secrets 清单。

## 6. 验收标准

- `codesign --verify --deep --strict` 对构建产物返回 `valid on disk` 与 `satisfies its Designated Requirement`。
- 未配置 Apple Secrets 时，CI 构建在 ad-hoc 校验步骤通过。
- 配置 Developer ID Secrets 时，CI 构建在 `spctl --assess` 与 `xcrun stapler validate` 步骤通过。
- 文档明确区分「ad-hoc 需放行一次」与「公证后零提示」两种状态。

## 7. 风险与回滚

- 风险：ad-hoc 签名仍会触发一次系统设置放行，用户可能误以为安装失败。文档已补充图形化操作路径。
- 风险：`hardenedRuntime` 默认开启，ad-hoc 签名在极端插件/动态库场景可能更严格；当前应用只依赖系统框架，本地实测通过。
- 回滚：删除 `bundle.macOS.signingIdentity` 配置、移除工作流中的签名配置与校验步骤即可恢复到旧行为；不影响业务代码与数据。

## 8. 后续

- 申请 Apple Developer 账号后，在仓库 Secrets 配置 `APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_SIGNING_IDENTITY`、`APPLE_ID`、`APPLE_PASSWORD`、`APPLE_TEAM_ID`，重新触发 `Desktop Build`，确认 `spctl`/`stapler` 校验通过后即可实现用户零提示。
- 发布下个版本时在 CHANGELOG 记录本次签名策略变更。
