# lizi-project 账户文档云存储·服务端集成点勘察报告

> 只读勘察，未修改任何仓库文件。仓库：`/Users/albertluo/workSpace/albertLuo/lizi-project`，后端根：`lizi-learning-management/`。

## 0. 结论摘要

1. **认证可直接复用**：C 端小程序登录 = 微信 `jscode2session` → 自动注册 `sys_user`（`wx_open_id` / `platform_identity`）→ `JwtUtils.sign(SysUser)` 下发 `X-Authorization-Lizi`/`Refresh-Authorization` JWT；鉴权层统一走 `JwtAuthenticationFilter` + `SecurityConfig.PUBLIC_PATHS`，业务侧一律用 `SystemTokenUtil.geUserInfoFromToken()` 取 `SysUser`（`user.id`）。新云存储接口无需自建登录，但**必须**考虑“已登录的游客匿名写草稿/资料归属”，建议复用 `X-Device-Id` 兜底（参考 MemberController `/miniProgram/member/me`）。
2. **存储现状是本地磁盘**，无 OSS/MinIO/COS：`common/FileUtil.uploadFile()` 按 MD5 重命名落盘到 `${SYS_DATA_URL}`（默认 `/app/upload_tmp/LiziFiles/`，本机 `user.dir`），WebMvcConfig 把 `/file/**` 映射到该目录；`spring.servlet.multipart.location=/app/upload_tmp/multipart`，上限 1024MB。文档云存储可以先把对象存储抽象成 SPI，默认本地实现，不做“先上 OSS 再回填”的返工。
3. **内容/版本结构已有成例**：`article`（title/content/file_path/author_id/cover_url/tags/status）+ `article_history`（article_id/version/title/content/file_path/remark）+ `ArticleServiceImpl.createHistory/rollbackArticle`，可直接照搬到“账户文档/笔记”表；`document` 表已有雏形但偏向 AI 题干上传，未承载用户云文档。
4. **接口落点明确**：新模块建议 `Controller: /miniProgram/cloud`（或 `/miniProgram/note`），`Controller 目录 lizi-learning/src/main/java/com/lizi/learningManagement/web/controller/MiniProgram/Cloud/`，Service/Entity/Mapper 放 `lizi-server` 对应包，沿用 MyBatis-Plus `ServiceImpl` + `LambdaQueryWrapper` + `Result<T>` + 分页（`com.baomidou.mybatisplus.extension.plugins.pagination.Page`）+ `jakarta.validation @Valid`。公开白名单默认**不放行**，即新接口默认登录可访问；游客匿名草稿如需放行，单列公开端点并自行判 token（参考会员 `/plans` `/me` 模式）。
5. **数据库规范**：`sql/` 下文件名 `yyyyMMddHHmmssfff_主题.sql` 或 `yyyyMMddHHmmss_主题.sql`，带头注释块 + `--default-character-set=utf8mb4` 执行提示 + `CREATE TABLE IF NOT EXISTS` + 唯一键/索引 + 审计字段（`created_at`/`updated_at`），写操作需留档并执行后用 `information_schema` 或 `SELECT` 回读验证。新表建议 `user_document`（账户文档）+ `user_document_version`（版本），复用 `article_history` 的版本模式。
6. **部署运行态**：容器端口 `5180`、context-path `/lizi`，Springdoc `/lizi/v3/api-docs`；生产 `note.lizipro.cn` 经前端代理 `127.0.0.1:5200` → 5180，公网 `https://note.lizipro.cn/lizi/...`；部署产物 `/usr/local/runtime/lizi-learning-1.0.0.jar`，环境文件 `/opt/1panel/runtime/java/lizi-learning-management/.env`，发布记录见 `docs/release/`。新上传/文件 URL 需注意当前 `/file/**` 是**相对路径**（`/lizi/file/...`），不会自动包含域名。
7. **docs 规范**：`docs/{decision,spec,plan,release,report,research}` 均存在，文件名 `<yyyyMMddHHmmssfff>_<主题>.md`；新调研/方案应落到 `docs/research` 或 `docs/spec`（本次勘察只写到 `/tmp`，不写仓库）。

## 1. 登录与身份（C 端账号体系 / JWT / 用户态）

### 1.1 登录入口

- 登录 Controller：`lizi-learning/src/main/java/com/lizi/learningManagement/web/controller/MiniProgram/WChatController.java`，映射 `/wx`：
  - `GET /wx/queryOpenId?code=&userName=&avatarUrl=&birthday=`（行 76 起）：调微信 `jscode2session`，拿 `openid`；库中无 `sys_user.wx_open_id` 则自动注册（`platformIdentity=1`，行 98-118），再 `sysUserService.updateLoginInfo` + `JwtUtils.sign`，把 `token/reToken` 写响应头（行 137-154）。
  - `GET /wx/getPhoneNumber` / `POST /wx/updatePhoneNumber`：手机号绑定（openid MD5 存 Redis `wx:openid:{md5}`，3 天）。
- 页面/H5 后台登录：`SysLoginController`（同模块 `Admin/System/`），走 `/user/login`、`/user/auth/**` 等。
- 未发现单独的“企业微信登录” C 端入口；主体是微信小程序 + sys_user。

### 1.2 JWT / Security

- `lizi-framework/src/main/java/com/lizi/framework/JWT/JwtUtils.java`：
  - 请求头常量 `AUTH_HEADER="X-Authorization-Lizi"`、`REFRESH_AUTH_HEADER="Refresh-Authorization"`、`ACCESS_TOKEN_TYPE/REFRESH_TOKEN_TYPE`（行 32-38）；`verify(token, username, tokenType)`（行 64-94）；`sign(SysUser)` 生成 access+refresh，claim 内置 `claimUserMap{id,username,rolesId,loginIp}`（行 119-167）；`blacklistKey` SHA-256 哈希防日志泄露（行 197-209）。
- `lizi-framework/src/main/java/com/lizi/framework/filter/JwtAuthenticationFilter.java`：`OncePerRequestFilter`，从请求头取 token → `JwtUtils.verify` → `sysUserService.findByUsername` + 状态校验 + Redis 黑名单 → 权限进 `SecurityContext`，`authentication.setDetails(user)`（行 70-125）；refresh 端点 `/user/checkReToken` 只收 refresh token；logout 允许同时携带 refresh 撤销。
- `lizi-framework/src/main/java/com/lizi/framework/config/SecurityConfig.java`：无状态 + `PUBLIC_PATHS`（行 31-56），C 端已放行 `/wx/**`、`/miniProgram/article/**`、`/miniProgram/knowledge/**`、`/miniProgram/company/**` 等；`/miniProgram/member/plans|me|pay/notify` 单独公开，其余 `anyRequest().authenticated()`；401/403 统一 JSON。
- **用户态工具类**：`lizi-framework/src/main/java/com/lizi/framework/JWT/SystemTokenUtil.java`：
  - `geUserInfoFromToken()` 返回 `SysUser`（行 30-34）；
  - `getUserIdFromToken()` 返回 `Long userId`（行 44-51）；
  - 依赖 `SecurityContextHolder`，无 ThreadLocal 自定义变量。新代码建议继续走 `SystemTokenUtil.geUserInfoFromToken()`。
- 用户表：`lizi-server/.../entity/SysUser.java`（`@TableName("sys_user")`）：`id`、`username`、`password`、`salt`、`phone`、`wx_open_id`、`platform_identity`、`avatar_url`、`my_back_img`、`login_ip/login_time`、`roles_id`、`is_deleted` 逻辑删除等。

### 1.3 用户态在 Controller 的取法

- 典型：`ProfileController`（`/wx/profile`）用 `SystemTokenUtil.geUserInfoFromToken()` 拿 `SysUser`，未登录返回 `Result.fail().code(401)`（行 40-50、`getCurrentUser()` 行 236-242）。

## 3. 文件上传现状（对象存储确认缺位）

### 3.1 本地磁盘为主

- 核心 util：`common/src/main/java/com/lizi/common/utils/FileUtil.java`
  - `resolveFileExt(MultipartFile)`（行 58-83）：优先原文件名后缀，否则按 MIME 兜底；
  - `uploadFile(file, fileType, filePath)`（行 385-400）：`SYS_DATA_URL` + relativeDir，扩展名白名单校验（IMG/VIDEO/DOCX/ZIP，行 40-47），MD5 重命名后 `file.transferTo`。
- 静态资源 Service：`lizi-server/.../service/impl/StaticResourceServiceImpl.java`：`upload()` 限制 50MB，落 `static/{type}/{category}/{md5}{ext}`；Entity `StaticResource` 记录 `fileName/filePath/fileUrl/fileSize/mimeType`（`fileUrl=/file/static/...`）。
- Controller 上传调用点：
  - 用户头像：`ProfileController.uploadAvatar()` `FileUtil.uploadFile(file, IMG, "avatar")` → `SystemConstant.getContextPath() + "/file/avatar/" + fileName`（行 213-224）。
  - 文章图片/博客：`ArticleManagement.uploadImage()` → `"/file/blog/"`
  - 后台管理静态资源：`StaticResourceController`。
- `/file/**` 资源映射：`lizi-learning/.../config/WebMvcConfig.addResourceHandlers()`（行 22-45）将 `lizi.DOWNLOAD_URL`（默认 `/app/upload_tmp/LiziFiles/`）和遗留 `/data/upload_tmp/LiziFiles/` 映射到静态资源；`GlobalStaticVariables.SYS_DATA_URL` 从配置注入。
- multipart：`application.yml` `spring.servlet.multipart.location=/app/upload_tmp/multipart`, `max-file-size/max-request-size=1024MB`（行 68-72），实际业务层还有 50MB（StaticResource）等更小限制。

### 3.2 对象存储现状

- 全仓未搜到 MinIO / OSS / COS / S3 SDK（`rg` 无命中）；存在 `HttpUtils`（common）面向 HTTP 工具，不含对象存储封装。
- **结论**：云存储功能若要做“账户文档”，当前唯一选择是自建存储抽象（`DocumentStorage` SPI）：本地实现维持现状，后续换对象存储只改 SPI 实现 + 配置，不改 Controller/Entity。

### 3.3 已有 `document` 表（偏向 AI 题干处理，不是云文档）

- Entity：`lizi-server/.../entity/Document.java`，`@TableName("document")`：`id,user_id,article_id,filename,file_path,file_type,status,content,created_at,processed_at`。
- Service：`DocumentServiceImpl`：上传到 `user.dir/upload/docs/` + 建记录 + 异步 AI 生成 QA。
- 可作为字段基线参考，但**不建议直接复用**为云存储主表（它绑定 article/QA 流程）。

## 4. 数据库现状与规范

### 4.1 sql/ 目录与 DDL 风格

- 目录：`lizi-learning-management/sql/`（含 `migration/`），文件名 `<yyyyMMddHHmmssfff>_<主题>.sql`（如 `20260806180000000_add_member_payment_tables.sql`、`20260810161451329_add_sys_agreement.sql`），也有少量 `yyyyMMdd_xxx.sql` 维护型脚本。
- 头部注释 + 执行纪律（文件 `20260806180000000_add_member_payment_tables.sql` 行 1-15）：
  - `@description / @author Albert_Luo / @email / @date` 注释块；
  - 明确“docker exec ... --default-character-set=utf8mb4 ... < file.sql”，防中文乱码；
  - `CREATE TABLE IF NOT EXISTS` 幂等，种子数据用 `WHERE NOT EXISTS` 守卫；
  - DDL 隐式提交，不开事务，逐条可重跑。
- 表设计模式：
  - 业务主键 `id BIGINT AUTO_INCREMENT`（会员表）或雪花 `BIGINT`（Article/StaticResource）；
  - 硬唯一键保障幂等/防重（`uk_order_no`、`uk_client_order_no`、`uk_transaction_id`、`uk_user_chapter`）；
  - `user_id BIGINT NOT NULL COMMENT '... sys_user.id'` 外键语义；
  - 状态字段用 `VARCHAR(32)` 状态机或 `TINYINT`；
  - 审计字段 `created_at DATETIME DEFAULT CURRENT_TIMESTAMP`、`updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`；
  - `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='...'`。
- 用户相关表：`sys_user`、`member_order`、`user_membership`、`chapter_unlock`、`user_notify_setting`、`user_word_book`、`learn_plan`、`practice_progress`、`question_note` 等，普遍以 `user_id` 归属。
- 已存在 document/attachment 类比：`document`（AI 题干）、`static_resource`、`rag_document`；**没有独立的“用户账户文档/附件”主表**。`ArticleHistory` 是唯一版本化内容表，可复用其“版本号+内容/文件路径-组合”结构。

### 4.2 推荐新表（落点建议，不落库）

- `user_document`（账户文档主表）：`id, user_id, title, summary, content (MEDIUMTEXT, markdown), file_path, file_type, tags, status (DRAFT/PUBLISHED/ARCHIVED), is_deleted, created_at, updated_at, UNIQUE(user_id, ...)`。
- `user_document_version`（版本快照）：`id, document_id, version, title, content, file_path, remark, created_at, UNIQUE(document_id, version)`，逻辑对齐 `article_history`。
- 若需“附件/对象”独立表：`user_document_attachment`（`document_id, file_name, file_path, file_url, file_size, mime_type, created_at`），对齐 `static_resource`/`Article` 的字段命名。

## 5. 文档/笔记类功能（可复用点）

### 5.1 Article + ArticleHistory（强复用）

- `Article`（`entity/Article.java`）：`title/content(Markdown)/file_path/author/author_id/summary/cover_url/tags/category/status/view_count/create_time/update_time/scheduled_publish_time/scheduled_withdraw_time/deleted_time/gen_qa`；映射 `article`。
- `ArticleHistory`（`entity/ArticleHistory.java`）：`id/article_id/version/title/content/file_path/create_time/remark`，映射 `article_history`。
- 实现：`lizi-server/.../service/impl/ArticleServiceImpl.java`
  - `rollbackArticle(Long historyId)`（行 311-329）：读取历史 → 重新 `createHistory` → 覆盖 article；
  - `createHistory(Article, remark)`（行 361-376）：`articleHistoryService.count` 算 version → save；
  - 博客同步见 `service/blogsync/ArticlePlatformSyncFacade` + `MetaWeblogClient`。
- **结论**：把 `article/ArticleHistory` 的“内容+版本”模式照搬到 `user_document/user_document_version` 是最短路径；甚至可以先做“云文档即文章”的窄方案，但不建议把账户私人文档直接塞进全局 `article`（涉及公开博客权限/审核/知识图谱收集）。

### 5.2 MetaWeblog / blogsync 是否适合接入

- 定位：`MetaWeblogClient` 是向 CSDN/博客园发布文章用的 XML-RPC 客户端（`buildNewPostRequest/buildEditPostRequest/executeNewPost/executeEditPost`），属于“文章→外部博客平台同步”，**不是**账户文档云同步协议。
- 如果你的“云存储”指跨端编辑/同步（text-editor 之类）→ 不需要 blogsync；如果将来要对外发布到博客平台，可复用 `ArticlePlatformSyncFacade`，与文档云存储解耦。

### 8.1 Controller 前缀

- 主入口：`/miniProgram/cloud/docs`（账户文档 CRUD/版本/收藏/分享），别名也可用 `/miniProgram/note`。
- 游客匿名草稿（可选）：`/miniProgram/cloud/anonymous` 单列公开白名单，控制器自行 `SystemTokenUtil.geUserInfoFromToken()` 判可登录用户，未登录用 `X-Device-Id`（对齐 MemberController `/me` 的游客模式）。
- 上传：`POST /miniProgram/cloud/docs/{docId}/attachments`（multipart）默认**不放进 PUBLIC_PATHS**，走 401 登录态。

### 8.2 表名建议

- `user_document`（账户文档主表）
- `user_document_version`（版本快照，结构参考 `article_history`）
- `user_document_attachment`（附件，可选；或先并入 `user_document.file_path` + JSON 附件元数据）
- `user_document_access`（分享/授权：`document_id, token_hash, permission, expire_at`，防遍历用哈希短码，不做明文文件 token）

### 8.3 认证复用点

- 请求头不变：`X-Authorization-Lizi` / `Refresh-Authorization`（`JwtUtils.AUTH_HEADER/REFRESH_AUTH_HEADER`）。
- 用户解析不变：`SystemTokenUtil.geUserInfoFromToken()` → `SysUser.id`。
- 公开白名单稳定：新接口默认 `anyRequest().authenticated()` 已覆盖；只把“游客草稿”所需端点加进 `SecurityConfig.PUBLIC_PATHS`，且该端点在 controller 内对 null user 走 deviceId 降级。
- 登陆后写人：所有写操作必须 `requireUserId`（仿 `MemberController.requireLogin()`）；删除/覆盖必须校验 `document.user_id == currentUserId`，防止越权改他人文档。

### 8.4 存储抽象

- 新增 `lizi-server/service/storage/DocumentStorage` 接口 + `LocalDocumentStorage` 实现（复用 `common/FileUtil.uploadFile` / `StaticResourceServiceImpl` 的落盘规范），配置 `lizi.storage.type=local`。
- 云文档内容文件与附件统一存相对路径，数据库存 `file_url`（相对 `/file/**`）与 `storage_key`；`DocumentStorage` 只暴露 `put/get/delete/url`，后续接 MinIO 只需新增 `MinioDocumentStorage` + 配置切换，不碰 Controller/实体。
- 初始化目录：沿用 `${SYS_DATA_URL}/cloud/{userId}/docs/`，权限目录按 userId 隔离，避免全仓共用 `/app/upload_tmp/LiziFiles` 导致越权访问 `/file/**` 时泄露他户文件（当前 `/file/**` 是公开静态映射，云文档私有内容必须另做访问鉴权：`storage_key` 不可预测 + controller 层鉴权，而不是裸 `/file/cloud/**`）。
- 分享下载：走带签名的 `token` 或短时效 controller 代理流，不把私有文件 URL 直接暴露到公开 `/file/**`。

### 8.5 风险与回滚

- **风险1**：`/file/**` 全公开，若云文档用静态路径存储，必须避免可枚举文件 URL（用雪花/哈希 + user 目录 + controller 鉴权）。
- **风险2**：`DocumentServiceImpl` 已有一版 `upload/docs` 本地方案，若直接复用 `document` 表会与 AI 题干流程耦合，建议另起表。
- **风险3**：大文件 1024MB 上限偏高；云文档建议限 20-50MB/文件，超过再走分片上传（MVP 不做）。
- **回滚**：新表 DDL 幂等 `IF NOT EXISTS` + 独立迁移文件，可安全回滚（删表仅影响新功能）；新 Controller 不触碰旧接口，回滚即移除新 jar 包并重启容器，发布前备份 jar + `.env` + `sql`（照 `docs/release` 模板）。
