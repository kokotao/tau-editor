### 4.1 R1：`emit('changed')` + `emit('edit-cloud-doc')` 与未分类归属 —— **通过**

- 顺序（`CloudDocTree.vue:1646-1652`）：`emit('changed')` → `emit('edit-cloud-doc', 合成节点)`。
  - `changed` 的宿主是**组件内部树刷新**（`CloudDocSidebar.vue:59` / `CloudDocBrowser.vue:178,320` 都是 `@changed="reload()"`），不触碰标签页，因此不会“重拉后把刚建的文件删掉”：云端 `save` 已返回成功，`reload()` 拿到的是包含新文件的服务端列表。
  - `edit-cloud-doc` 由 `App.vue:1377-1422` 消费，**按 `cloudFileId` 去重**（`tabsStore.tabs.find(tab => tab.cloudFileId === fileId)`），新建文件一定是新 fileId → 不会重复开标签；再次右键「打开」走的是 same fileId 的「已打开」分支。
- 未分类不造假分组：`menuCreateFile` 对 `group:uncategorized` 传 `fileCategoryId = categoryIdOf(node) = null` 且 `fileCategoryName = ''`（`CloudDocTree.vue:1385-1391`），`createCloudDocFile` 归一成 `category:null / categoryId:null`（`cloudDocCreateService.ts:136-144`）；后端新建分支直接落 null（`CloudDocServiceImpl.java:318-319`），分组树把它放进 `uncategorizedFiles`（`cloudBrowserService.ts:291-308`）→ **不会产生 `custom:未分类` 假分组**。合成节点的 `file.category/categoryId` 也同步为 null（`CloudDocTree.vue:1667-1692`），不会误导属性面板。
- 空正文可打开：`inlineText(0 字节)` → `''`，`readDocumentContent` 走非 null 分支返回 `''`（`CloudDocServiceImpl.java:738-751、806-814`），`materializeCloudDocForEdit` 的 `content === null` 判断不会误杀 → 标签页打开空文档成立。
- 无工作区时（D2 兜底 `tau/<分类>/<文件名>`，三段路径）能被 `parseCloudDocEditPath` 正常解析（至少三段 + `tau` 前缀），落位到 `cloud_scratch_workspace`，不依赖用户工作区 → 验收「无工作区时按 D2 兜底创建成功」成立（仍需一次真机点击确认，见 §6）。

### 4.2 R2：`cancelled` 重置 / `rows` 引用 / conflict 语义 —— **通过（1 条 P1 文案问题见 P1-3）**

- **`cancelled` 会重置**：`menuUploadFiles` 每次都整体替换 `uploadDialog.value`，其中显式 `cancelled: false`、`summary: null`、`done: 0`（`CloudDocTree.vue:1428-1440`）；`startUpload` 里 `isCancelled: () => uploadDialog.value.cancelled` 读的是**当前**引用（`:1476`）。因此「中止一次 → 再上传一次」不会被上一轮的取消位卡死。
- **`state.rows` 与渲染行是同一引用**：`rows` 来自 `plan.map(...)` 存进 `ref` 对象，`startUpload` 的 `const state = uploadDialog.value` 拿到的是同一个响应式代理；回调里 `uploadDialog.value.rows[index].status = …` 改的是同一批行对象 → 进度条/行状态实时更新。组件测试实测 `data-status` 由 `pending` 变 `done`（`CloudDocTree.test.ts` R2 用例）也印证了这点。
- **`conflict` 不会被误当成功**：`runBatchUpload` 里 text 的 `conflict` → `{status:'skipped', kind:'conflict'}`（`cloudDocBatchUploadService.ts:244-246`）、binary 的 409 → 同样 `skipped`（`:275-277`），汇总只进 `skipped` 不进 `ok`；UI 另外把行文案换成「云端已存在同名文档，未覆盖」（`CloudDocTree.vue:1483-1488`）。
- 附带确认：`aborted` 的两种来源（用户取消 / quota+unauthorized）在**计数**上是准确的（中止后不再计入剩余项），只是**文案**不区分 → P1-3。
- 并发安全：上传中 `busy=true` 会禁用关闭（`CloudDocUploadDialog.vue:87`、遮罩 `:189-194`、Esc `:196-202`），且 `closeUploadDialog` 在 busy 时直接 return，因此不存在「队列在跑但 rows 被清空」的孤儿写入。

### 4.3 R3：递归收集边界 / 截断统计 / 分类兜底 —— **通过，1 条 P1（白名单）**

- `node_modules` 类目录：`shouldSkipEntry` 对**目录**做 `SKIP_DIR_NAMES.includes(name.toLowerCase())`（大小写不敏感，`NODE_MODULES` 也拦），隐藏项单独拦（`cloudFolderUploadService.ts:92-101`）；`node_modules` 只记一条「构建或依赖目录」跳过，不再下钻。
- 大小写 / 嵌套：目录名按小写比较；嵌套靠 `walk` 递归 + 路径拼接 `joinLocalPath`（保留根盘符风格），`relativePath` 统一 `/` 用于展示。
- 符号链接：Rust `list_files` 用 `entry.metadata()`（不跟随符号链接语义，`frontend/src-tauri/src/commands/file.rs:729-763`）→ 链接目录会被当成 `file` 上报，**不会造成无限递归**；最坏情况是把它当文本文件传一次并逐条失败。另有 `maxDepth=8` / `maxFiles=500` 双上限兜底。
- `listFiles` 抛错：单个目录读取失败只推一条 `skipped{reason:'无法读取目录'}` 并继续（`:245-257`），不中断整体收集。
- 文件上限截断的「跳过数」：截断时 `truncated=true` + `truncatedReason='文件数超过 500 个上限，已截断'`（`:311-316`），并且在**确认页**用独立黄色提示行展示（`CloudFolderUploadDialog.vue:40-46`），与「将上传 N / 跳过 M」分开 → 用户不会误以为全部上传；但 `skipped` 列表在命中 hardStop 后不再补全（后续的不可上传文件不会被列出），这是刻意的取舍，可接受。
- `ensureCategoryForFolder` 三级兜底不会「静默放错」：新建成功 → 用新 id；失败 → 查同名复用；再失败 → 自由文本并回 `note`（`:345-376`）。关键的是：**二进制通道后端也会按 category 名 find-or-create**（`CloudDocBinaryServiceImpl.java:225-243`），所以即使退化到自由文本，二进制文件最终也会落到真实分类；文本文件则依赖「同名唯一」匹配（`cloudBrowserService.ts:278-290`）。残留风险（同名多义、旧 categoryId 被 keepOr 保留）已记为 P2-8。
- 默认不覆盖：见 §4.2 的 conflict 结论；文本走的正是 `syncDocumentByPath` 的三方决策，`pull/conflict` 且未传 `overwrite` 时直接返回 conflict（`cloudSyncService.ts:744-752`）。
- 唯一的实质问题就是 P1-1（前端白名单比后端多 25 项 → 失败而非跳过）。

### 4.4 R4：blob 生命周期 / JSON-blob 判定 / el-dialog 关闭语义 —— **通过，1 条 P1（重试入口）**

- blob 释放：只有一个 `objectUrl` 变量，`createObjectUrl` 先 `releaseObjectUrl`（`CloudDocPreviewDialog.vue:239-252`）；`loadPreview` 入口、`handleClosed`、`onBeforeUnmount` 三处都会释放（`:312、:373-384、:395-398`）。
  - 连续点击两行：`loadSeq` 递增 + 每个 await 后 `if (seq !== loadSeq) return`，旧回包丢弃；旧 URL 在新 load 开始时已被释放，不会串图。
  - 关闭动画中重开：`handleClosed` 用 `props.visible` 守卫（重新打开时**不**释放新一轮的 URL），这是正确写法。
  - 请求失败：异常路径不创建 URL（先 `assertNotJsonBlob` 再 `createObjectUrl`），无泄漏。
- `assertNotJsonBlob` 不会误判正常 PDF：判据是 `blob.type` 是否含 `json`，PDF 响应是 `application/pdf`；且该函数对非 JSON 直接 return（`:293-307`）。真正需要它的原因核对成立：后端统一异常处理器把 `{code,message}` 以 **HTTP 200 + application/json** 返回（`GenericExceptionHandler.java:39-44`），而 `request.download` 对 Blob 响应直接放行（`utils/http/index.ts:129、241-256`）→ 不识别就会把错误体当 PDF。残留的漏判场景（text/html、空 content-type）见 P2-14。
- `el-dialog + destroy-on-close + v-model computed`：`destroy-on-close` 只销毁默认插槽内容（`PdfPreview`/`img` 随之卸载），**不卸载**弹窗组件本身，所以 `@closed` 的收尾与 `onBeforeUnmount` 互不冲突；`v-model` 的 setter 只在 `false` 时 `emit('close')`，父组件 `@close="previewVisible = false"`（`index.vue:83-87`）→ 关闭语义正确。`close-on-click-modal=false` 但 Esc 仍可关（走同一 setter），符合预期。
- 错误文案映射与后端一致：`preview.pdf`/`download` 的 404（非 owner/非 BINARY）→ 后端 message 原样展示；422（转换中）→ 固定文案；401/403 → 固定文案（`:277-285`）。与 `OfficePreviewServiceImpl.java:66-77` 的 422 口径一致。
- 唯一问题是 P1-2（PDF 分支失败后没有重试入口，提示语自相矛盾）。
