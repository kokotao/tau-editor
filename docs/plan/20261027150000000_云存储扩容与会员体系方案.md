补充口径：

1. **8 GB 老账号容量保留**：作为 `permanentBytes` 永久配额长期保留，不参与任何降级/到期计算；这类账号即使不订阅也不会掉到 1 GB。
2. 免费 1 GB 对纯文本足够（Markdown 正文平均 40 KB/篇 ≈ 2.5 万篇），真实瓶颈是附件图片；所以差异化卖点是容量、单文件上限、版本与附件能力。
3. 团队版需要成员管理、共享池分配与审计，工作量最大，确认推迟，接口设计先不做（见 §5 标注 deferred）。

## 3. 签到与奖励机制（已拍板：随机 + 滑动窗口 + 累计封顶）

奖励**只加临时容量**，不替代付费档位。规则：

| 机制 | 规则 |
|---|---|
| 每日签到 | 获得**随机**容量 **+20 ~ 120 MB**（服务端生成随机数，客户端不参与）；当天容量条立刻可见增长 |
| 滑动窗口过期 | 每份奖励**自获得起保留 30 天**，逐日滚动过期（第 31 天那份自然失效）；稳态有效奖励约 `30 天 × 期望 70 MB ≈ 2.1 GB` |
| 连续签到加成 | 连续第 7、14、21… 天（每满 7 天）**当日奖励翻倍**；连签天数不设上限，但只影响当天这一笔 |
| 累计封顶 | **终身累计奖励容量 ≤ 10 GB**；达到后签到仍记录天数/积分，但不再增加容量（避免"签到攒出无限空间"） |
| 断签 | **不清零已有容量**：已发放的奖励按各自 30 天窗口自然过期；断签只让当日随机基数回落（加成中断） |
| 容量优先级 | 永久配额（含 8 GB 老账号）→ 付费档位 → 签到临时容量 |
| 过期影响 | 只影响"还能不能上传"；**已存文档/附件一律不删** |
| 到期提示 | 奖励容量池总量在未来 7 天内将下降时提示一次（不逐日打扰） |

计算示例（期望值，供核对实现）：连签 30 天、每天均值 70 MB，第 7/14/21/28 天翻倍 →

```
月内发放 ≈ 22×70 + 8×140 = 1540 + 1120 = 2660 MB ≈ 2.6 GB
稳态有效（30 天窗口）≈ 2.6 GB，终身累计约 2.6 GB/月，约 4 个月触达 10 GB 封顶
```

反作弊三条硬要求（写进后端实现）：

1. 签到**只认服务端时间**，客户端时间仅用于展示；
2. 唯一约束 `(user_id, checkin_date)` + 设备指纹，重放请求不产生二次奖励；
3. 随机量用**服务端随机源**并落流水表（append-only：`granted_bytes / expires_at / source`），余额由流水汇总，禁止直接改余额字段。

## 4. 超额与降级策略

| 场景 | 行为 |
|---|---|
| 用量 > 有效配额 | 「超额只读」：可打开/下载/删除/继续编辑本地，**不能新增文档与附件**；顶部常驻提示 + 扩容入口 |
| 超额宽限 | 30 天内不限制读取；到期仍超额保持只读（数据不删） |
| 订阅到期 | 提前 7/3/1 天提醒；到期后降为「永久配额 + 免费 1 GB」，超出部分只读；8 GB 老账号不受影响 |
| 奖励容量过期 | 有效配额随之下降，可能进入超额只读；提示文案明确指出"签到容量已过期" |
| 删除释放 | 彻底删除立即释放；回收站（逻辑删除）不释放，需在回收站提示 |
| 版本占用 | 版本行不计入配额（现状），无需引导用户清版本；后台 blob GC 跟上（见 §3.6 旧方案） |
