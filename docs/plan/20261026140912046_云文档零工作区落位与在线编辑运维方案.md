- 关联：`docs/spec/20261024174525300_账户文档云存储Tau同步lizi方案.md`、`docs/plan/20261025173000000_Markdown相对图片附件同步方案草案.md`

## 0. 结论先行

1. **取消"必须先打开工作区"的前置门禁**，改为"落位解析链"：能根据云文档路径 + 本机最近项目静默定位到原工作区就直接打开；定位不到就静默落到 `tau-scratch/{workspaceName}` 临时工作区继续编辑。
2. **落位（本地目录）与身份（云路径）解耦**：云路径 `tau/{workspaceName}/{relative}` 才是文档身份，本地目录只是编辑缓冲。因此落进临时区**不会**让文档"搬家"，保存回云端的 path 保持不变。这是整套方案成立的前提。
3. 在线编辑不引入协同内核，走**"单写者 + baseVersion 乐观锁 + 本地草稿"**的主流轻量路线——服务端**已经**实现了 409 乐观校验，缺的全在客户端编辑态与运维面。
4. 有工作区时不静默切走：加开的规则只对"当前没有工作区"生效，避免打断用户上下文。
5. 只读判定**不需要新增字段**：`UserDocument.userId` 即 owner、`UserDocument.visibility` 即可见性，两者都在。

## 2. 方案 A：云文档零工作区落位

### 2.1 设计原则

- **locate ≠ identity**：本地目录是"编辑缓冲"，云 path 是"身份"。落位失败绝不改变文档归属。
- **静默 ≠ 无声**：不弹对话框，但必须有可撤销的一行提示（状态栏 toast），否则用户不知道自己在哪个目录里敲字。
- **不打断**：只有"当前没有工作区"才允许自动开；有工作区时不切走。

### 2.2 落位解析链（5 级，纯函数，可表驱动单测）

```
resolveLanding(cloudPath, ctx) -> Landing
  ctx = { currentWorkspacePath, currentWorkspaceName, bindings, recentProjects, appDataDir }

L0 非法路径            -> Reject（沿用 validate_cloud_doc_path）
L1 当前工作区名 == wsName  -> inPlace
     （用户就在目标工作区里，零成本）
L2 bindings[wsName] 目录仍存在 -> silentOpen(binding.path)  // 静默打开
L3 recentProjects 中 basename == wsName 且目录存在 -> silentOpen(recent.path)，并写回 binding
L4 bindings[wsName] 存在但目录已被删/改名 -> scratch(wsName, staleBinding=true)
L5 无任何线索 -> scratch(wsName)
```

**当前有工作区但名字不匹配（跨工作区文档）时，保持现行为不变**：走 `CLOUD_PATH_NOT_IN_WORKSPACE` → 只读预览 / 另存为。理由：自动把用户从 A 项目切到 B 项目，属于上下文劫持。

### 2.3 临时工作区（scratch）语义

- 目录：`{appDataDir}/tau-scratch/{wsName}`（`wsName` 为空时用 `_unnamed`）。
- **不写入 `recentProjects`**（避免污染"最近项目"列表），但**写入 bindings**，作为下次的"上次落点"。
- **标识只在资源管理器徽标**（`临时工作区 · 来自云文档 <path>`，并提供 `另存到工作区…`）——**已定：标题栏不展示 scratch 标识**，避免抢主标题注意力。
- 与 `single-file` 模式的区分：不复用 `single-file`（那会让 `isPathInWorkspace`、`hasWorkspace` 等既有分支全线改判）；改为在 workspace 模式下增加一个来源标记：

```ts
// stores/workspace.ts
type WorkspaceOrigin = 'user' | 'silent' | 'scratch';
state.workspaceOrigin: WorkspaceOrigin = 'user';
state.workspaceBindings: Record<string, { path: string; lastUsedAt: number; origin: WorkspaceOrigin }> = {};
```

存储：独立的 localStorage key（例如 `text-editor-cloud-workspace-bindings`），不与 `text-editor-workspace` 混存，便于单独清理/迁移。

### 2.4 交互细则

| 场景 | 行为 |
| --- | --- |
| 无工作区，绑定命中 | 打开该工作区 + 打开文档 + toast `已自动打开工作区「分享」`（含"切换工作区"链接） |
| 无工作区，绑定未命中但最近项目命中 | 同上，toast 追加 `（来自最近项目）` |
| 无工作区，全部未命中 | 建 scratch，toast `未找到原工作区，已在临时工作区中打开` |
| 无工作区，绑定目录已失效 | 建 scratch，toast `原工作区已不存在（<path>），已在临时工作区中打开` |
| 有工作区且匹配 | 直接落当前工作区（现行为） |
| 有工作区不匹配 | 现行为（只读预览 / 另存为），不静默切换 |
| scratch 中存在未保存草稿时关闭 | 提示一次（复用草稿机制，见 3.2） |

### 2.5 后端改动

`cloud_doc_open_target` 的 `workspace_root` 改为可选语义：空串不再返 `INVALID_ARGUMENT`，而是调用新的纯函数 `resolve_cloud_doc_landing` 返回 `Landing`（含 `landingKind` / `workspaceRoot` / `workspaceName` / `staleBinding`）。
纯函数放 Rust 侧的理由：与 `decide_cloud_open_action`、`cross_workspace_open_target` 一致，可 `#[cfg(test)]` 表驱动覆盖大小写、分隔符、重复 basename 等边界。

> 备选：全部放前端。**不推荐**——路径规范化（`MAIN_SEPARATOR`、`\\`↔`/`、尾斜杠、Windows 大小写）在 Rust 侧已有实现，重复实现会产生两套真相。

### 2.6 已知缺陷与中期方案

**同名目录歧义**：`workspaceName` 是 basename，`D:\a\proj` 与 `D:\b\proj` 同名，云路径无法区分。
- 本期缓解（**已定，可接受**）：bindings 以 `wsName` 为键 + `lastUsedAt` 最近优先；多候选时不静默猜，走 L5 临时区（宁可临时区，不可写错目录）。
- 中期（另立需求）：云路径引入 workspace 稳定标识段（如 `tau/_ws/{shortHash}/{relative}`），需服务端双写 + 历史路径迁移，不在本期范围。

## 3. 方案 B：在线编辑 / 更新 / 运维

### 3.1 分档与取舍

| 档 | 内容 | 后端依赖 | 建议 |
| --- | --- | --- | --- |
| T0 | 现状：显式保存，手动点 | 无 | 不满足"在线编辑"体验 |
| **T1（推荐本期）** | 单写者 + baseVersion 乐观锁 + 自动保存 + 本地草稿 + 冲突三选一 | **已就绪** | 主流轻量路线，≈SaaS 文档编辑器的单机形态 |
| T2（Roadmap） | CRDT/OT 实时协同（Yjs + Monaco binding + WebSocket） | 需服务端协同通道 | 成本一个数量级，待 T1 数据支撑需求 |

选 T1 的理由：服务端 409 乐观锁已经实现并有测试覆盖，客户端只差编辑流水线；T2 需要服务端新增长连接与冲突合并内核，在"多端并发编辑"需求被真实观测到之前投入不划算。

### 3.2 T1 编辑流水线

```
openDocument(fileId)
  └─ cloud_docs_get → 记录 { fileId, version, contentHash } 作为 baseVersion 基线
  └─ 探测本地落点（方案 A）→ 有本地同内容文件则直接挂到本地文件，否则用云端内容开临时缓冲

编辑中
  ├─ debounce 2.5s 空闲 / 失焦 / Ctrl+S → 触发保存
  ├─ 单飞队列：同一 fileId 同时最多 1 个请求在飞，期间的修改合并成"最新内容"
  ├─ 空写抑制：contentHash 未变 → skip（省流量、省版本号）
  └─ 本地草稿：{ fileId, content, baseVersion, savedAt } 落盘，异常退出可恢复

保存
  ├─ 成功 → 更新基线 version/contentHash，状态栏 ✓
  ├─ 409   → **不自动重试**：拉取最新版 → 弹三选一（保留我的 / 用云端 / 另存副本）
  ├─ 413   → 配额提示 + 给出当前占用
  └─ 网络  → 指数退避重试（上限 N 次），期间以草稿为准，状态栏"离线，已暂存"
```

要点：

- **客户端哈希判定是 first line，服务端 baseVersion 是唯一权威**。现有 `decideSyncAction` 的三方哈希只能发现"我这边看到的变化"，两个客户端几乎同时保存时只有 409 能拦住。
- 409 的处理**绝不能自动覆盖**，否则乐观锁形同虚设。
- **只读态判定用现有字段，不新增**：`UserDocument.userId` 是 owner（`UserDocument.java:30`），`visibility` 是可见性（`:69`）。前端按 `detail.userId == session.userId` 切 `readOnly`，保存按钮置灰并说明原因；服务端 owner 校验由 `BlogCloudDocUpdateRequest` 路径承担——前端判定只是体验优化，**不作为安全边界**。

### 3.3 更新（覆盖）与新建的语义收口

- `baseVersion = null` → 新建；`baseVersion = 当前版本` → 覆盖。这条规则服务端已强制（`CloudDocServiceImpl.java:293-345`），客户端**必须**透传，不允许"不传就覆盖"。
- 恢复历史版本前，先自动把当前内容存一版，防止"回滚后想撤销回滚"变成不可逆操作。

### 3.4 运维设计

| 维度 | 设计 |
| --- | --- |
| 日志 | 每次保存记 `deviceId + fileId + baseVersion + result + latency + conflict?`，与现有 `X-Device-Id` 头对齐 |
| 指标 | 保存成功率、409 冲突率、保存 p95 延迟、草稿积压条数、scratch 目录体积 |
| 版本保留 | **已实现，本期不改**：`maxVersionPerFile = 30`（`CloudDocProperties.java:32`，可用 `lizi.cloud-doc.max-version-per-file` 覆盖），`trimVersions()` 每次保存后裁剪，只删版本行、不删文件（`CloudDocServiceImpl.java:772-786`）。30 条足够覆盖"改错了想回退"的真实窗口，加"每日快照"要新增表与定时任务，收益不抵成本 |
| 存储 GC（**缺口，规则已定**） | 版本行被裁剪、文档行被逻辑删除后，`storageKey` 指向的 blob **永不回收**（`CloudDocServiceImpl.java:75` 明确 V1 不做内容/文件清理）。规则：**引用为零即删**——不做天数兜底、不做容量水位。实现见 3.6。**后端另立需求，不阻塞本期** |
| 临时区清理 | 启动时清理 `tau-scratch/*` 中 7 天未触碰**且已无未保存草稿**的目录；有草稿一律保留并在进入时提示 |
| 配额 | 413 提前预检（已用 + 新增 − 旧版本），避免长文写完才失败。**口径已核实：配额只算存活文档行，不算残留 blob**（`UserDocumentMapper.java:37` `SUM(size) WHERE is_deleted = 0` + 附件），因此 GC 不会改变用户看到的已用空间，纯属磁盘运维 |
| 回滚演练 | 季度走一次 `versions/restore` 全链路，确认版本链未断 |

### 3.5 验收标准（可执行）

1. 无工作区点击云文档 → 1.5s 内出内容，且 toast 明示落位来源（绑定/最近/临时）。
2. 绑定命中场景不出现任何模态框。
3. 绑定目录被手动删除 → 自动降级临时区，不报错、不丢内容。
4. 两个客户端先后保存同一文档 → 后者收到 409 并进入三选一，不静默覆盖。
5. 编辑中强杀进程 → 重启后草稿可恢复，且 baseVersion 仍为旧值（下次保存触发 409 而非误覆盖）。
6. 落位到 scratch 后保存 → 云端 path 与原文一致（无"搬家"）。
7. `cargo test` 覆盖 `resolve_cloud_doc_landing` 的表驱动用例；vitest 覆盖落位解析的 5 级分支。

### 3.6 存储 GC（引用为零即删）

**名词先说人话**：云文档正文有两种存法——① 数据库行里的 `content` 字段，只冗余存 ≤1MB 且合法 UTF-8 的正文（`CloudDocServiceImpl.java:716-736`）；② **磁盘上的物理文件**，行里只留一个 `storage_key` 指针，实际路径由 `LocalDocumentStorage` 拼在 `SYS_DATA_URL` 下（`LocalDocumentStorage.java:113-114`）。本节说的 **blob 就是第 ② 种物理文件**；这词是从对象存储借来的，在本项目里等价于"存正文的那个磁盘文件"。

**孤儿怎么来的**：每次保存都会写一个新文件 + 插一条版本行（`insertVersion`，带 `storage_key`）；`trimVersions()` 把超过 30 条的**版本行**删掉，但**不删文件**（`CloudDocServiceImpl.java:75` 明写 V1 不做内容/文件清理）。于是行没了、文件还在、谁都不指向它——既不在任何列表里，也不计入配额，纯占磁盘。

**规则（已定）**：blob **没有任何行引用就删**。不用天数兜底、不用容量水位、不用"保留最近 N 个孤儿"。

引用源（四张表都有 `storage_key`：`UserDocument.java:42`、`UserDocumentVersion.java:38`、`UserDocumentAsset.java:41`、`UserDocumentPreview.java:34`）：

```
orphans = { 文档存储根下的所有 blob }
        - { user_document.storage_key        /* 含 is_deleted=1 的行，逻辑删除仍算引用 */ }
        - { user_document_version.storage_key }
        - { user_document_asset.storage_key }
        /* 预览缓存由现成的 previewCleanupJob 自理，GC 不进入预览目录 */
```

三条必须写进实现的边界：

1. **`is_deleted=1` 的行仍算引用**。逻辑删除是"留行以便审计与同路径重建"（`CloudDocServiceImpl.java:492`），把它的 blob 删掉等于把逻辑删除变成物理删除。**这里按保守口径取定**：回收站内的物理内容保留；若日后磁盘吃紧，可改为把 `is_deleted=1` 也算孤儿，代价是这些文档彻底不可恢复、同路径重建也回不到旧内容——届时再评审，不预留开关。真正的孤儿来源只有一个：`trimVersions()` 删掉的版本行（`CloudDocServiceImpl.java:772-786` —— 只删行、不删文件）。
2. **扫描顺序是先收集后删除，且加最短存活窗口**（如 mtime < now-24h 才进候选）。这不是保留策略，是防竞争：保存路径先落盘/先插行取决于具体分支，窗口用来避开"blob 已写、行还没插"的那一瞬间。
3. **两阶段**：先 dry-run 输出候选清单与字节数，进日志；确认量级合理后再开删。首次上线只跑 dry-run。

落点：复用现成的 `CloudDocMaintenanceJobHandler`（xxl-job，已有 `previewCleanupJob` 与分享明细清理），新增 `cloudDocBlobGcJob`，参数沿用 `key=value` 风格（`dryRun=true&graceHours=24`）。

**为什么这条不紧急、也不影响用户**：配额口径是 `SUM(size) FROM user_document WHERE is_deleted = 0` + 附件（`UserDocumentMapper.java:37`、`CloudDocServiceImpl.java:649-653`），残留 blob 从来不计入。所以 GC 不改变任何用户看到的已用空间，也**不会**让 413 变松——它只解决磁盘单调增长。

### 6.2c 本轮真正抓到的缺陷（都已修，值得后人记住）

1. **追加保存带过期基线起飞**（`cloudDocSaveController` 初版）：单飞队列会在 `schedule` 续体醒来**之前**派发下一次保存，于是"起飞时读 session.baseVersion"读到的是尚未应用上一次成功值的旧基线 → 合并保存凭空 409。修法：把 `applySaveResult` 挪进 `dispatchLane`，出队顺序与基线推进顺序强制一致。
2. **假绿测试**：`autoSaveScheduler` 最初用假计时器，"同 hash 不发请求"那条在触发根本没跑到时也成立。改用真实计时器 + `sleep` 后才是有效断言。**教训：`not.toHaveBeenCalled()` 必须有阳性对照。**
3. **切到本地标签时的保存空洞**：切到另一个云文档会 `open()` 让旧 Lane 失权，但切到**本地标签**不触发 `open()`，旧 Lane 仍活着，队列里的追加保存可能发出去。修法：`save` 回调派发时同步复核 `tabs.some(tab => tab.cloudFileId === fileId)`（`App.vue:1029-1032`）。
4. **换文档竞态**：用 `Lane`（fileId 的完整上下文）整份替换 + `activeLane !== lane` 引用相等判失权，而不是计数器——没有回绕、没有漏加。
5. **scratch 来源在会话恢复时被洗成 user**：`App.vue` 的 `restoreSession` 调 `openWorkspace(path)` 不传 origin（默认 `'user'`），导致徽标消失、临时区被写进"最近项目"，且**第二次重启后冷启动兜底失效**。修法：路径未变时沿用持久化的 origin。
6. **失效路径的恢复是"静默空树 + 徽标撒谎 + 每 1.5s 一条 warn"**：`loadFromStorage` 无存在性校验，`resolve_workspace` 的 `WORKSPACE_NOT_FOUND` 被 `console.debug` 吞掉，`fileSystemStore.error` 全仓无人读，watcher 退化到 1.5s 轮询并无限 `console.warn`。修法：`services/scratchWorkspaceGuard.ts` 冷启动早于所有下游校验，**只在"确认不存在"时清上下文**（探测返回 `null`/抛错一律保留），且不重建目录。

### 6.3 Rust 验收：必须用 MSVC 工具链

`cargo test --lib`（本机默认 `stable-x86_64-pc-windows-gnu`）在本项目**跑不起来**，与代码无关：

- `tauri-runtime-wry` 引用 `TaskDialogIndirect`（只存在于 WinSxS 的 comctl32 **v6**）；
- `tauri-build` 通过 `rustc-link-arg-bins` **只给 bin 目标**注入 comctl32 v6 清单，测试目标没有；
- 加载器因此绑到 legacy comctl32 v5 → 测试 exe 在进 main 前即 `0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND` 退出；
- GNU 侧无法在 build.rs 层修复（mingw 内置默认清单优先，同一 .rsrc 只认第一份）。

**验收命令（正式）**：

```bash
cd tau-editor/frontend/src-tauri
cargo +stable-x86_64-pc-windows-msvc test --lib
# → test result: ok. 109 passed; 0 failed
```

**产品本身无风险**：清单只注入 bin，app 本体有清单；"启动即崩"不成立。
**不引入 `rust-toolchain.toml`**：为跑测试而改全项目构建目标，副作用大于收益。
